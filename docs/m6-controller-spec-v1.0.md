# Chess Engine Lab — M6 Headless Controller and UCI Specification v1.0

**Status:** APPROVED FOR M6 — D84–D105 approved individually; user explicitly delegated and pre-approved the remaining M6 design decisions D106–D117 on 2026-10-20. This document records their concrete resolution. Implementation remains gated on merging this specification and the separate approved M6 Codex kickoff into `main`; implementation ends at an unmerged PR for review.  
**Milestone:** M6 — native UCI executable, Node.js/TypeScript headless controller/CLI, authoritative chess games and clocks, external engine sessions, reproducible experiments and recoverable local records.  
**Baseline:** merged M1–M5, `docs/architecture-v1.0.md`, `docs/m3-search-spec-v1.0.md`, `docs/m4-search-spec-v1.0.md`, `docs/m5-transposition-table-spec-v1.0.md`, `docs/evaluation-abi-v1.0.md`, current C++ headers/tests, native and pinned WASM CI. This specification refines M6 and does not authorize changing M1–M5 semantics or implementing deferred search experiments.

## 3. Native UCI executable: exact search/decision bridge

Create a separate native executable linked to existing C++ ChessCore, Evaluator and M4/M5 Search; keep C++ core free of UCI, OS process and Node dependencies. Build native-only (`NOT EMSCRIPTEN`) and keep all existing WASM tests/configurations intact. The executable must start with a reliable default evaluator available in native build/test distribution, while allowing an explicitly selected compatible native evaluator module and effective JSON configuration. Never modify the M2 ABI.

**Handshake and parser.** Reply to `uci` with stable `id`, advertised actually supported `option` declarations and `uciok`. `isready` responds with `readyok`, including while a worker is active, without mutating active search resources. `setoption` and `ucinewgame` changes affecting position/evaluator/TT are serialized with idle/search completion; do not mutate evaluator or table during search. Preserve ordinary UCI `position` commands, including move legality/replay validation. For `position fen`, a FEN carries clocks but not prior occurrences; supply incomplete `GameHistory` even if appended moves are known. Invalid FEN/moves/options are diagnosed and must not replace the last valid state with a partial parse. For `ucinewgame`, default to retaining valid M5 caches unless explicit `Clear Hash`; M5 exact evaluator/history compatibility still applies.

**Worker lifecycle.** Main command/output path reads stdin continuously; one search thread calls `iterative_search()` synchronously with a fresh cancellation source and immutable root/history/config. `stop` requests cancellation (including during TT probes), joins/resolves worker, then emits final output once. No overlapping evaluator/TT use or races on `position`, `setoption`, `quit`. `quit` cancels, joins, disposes safely. Handle EOF, repeated `stop`, contradictory/malformed `go` and exception paths predictably. `isready` must never block waiting for an unbounded search completion. No pthread requirement is introduced for the existing WASM search library.

**Search modes and clock distinction.** Support explicit `go depth 1..64`, `go movetime ms`, `go infinite`, and conventional UCI remaining-time/increment fields with a bounded, documented deterministic *adapter-local* time-allocation policy. The Chess Lab **controller** remains the authoritative game-clock owner and independently enforces `stop`; the adapter's own scheduler merely allows it to function under ordinary third-party UCI GUIs. `go infinite` must not emit an unsolicited `bestmove` at M4's depth-64 safety ceiling: retain the last completed result and await `stop`. A fully exhausted depth cap may be reported as an information string. `go depth` finishes when depth reached; `go movetime` finishes at local deadline or appropriate earlier terminal. Validate durations and overflow. `go wtime...` uses a documented, conservative allocation that never intentionally exceeds remaining time and handles very small/zero budgets safely. No `ponderhit`/`searchmoves` semantics claimed. Standard UCI `stop` after an already delivered `bestmove` is harmless.

**Exact progress/score output.** Emit `info depth`, elapsed ms, nodes and `multipv` only for committed completed-depth snapshots. PVs contain only actually played legal moves, not announced claim intentions. Emit `score mate` only for sound mate scores in UCI side-to-move perspective with correct ply-to-move rounding (including root/terminal edge cases). Finite M2 score is arbitrary White-positive, **not automatically centipawns**: unless explicitly calibrated by an approved mapping, emit truthful `info string chesslab score raw ...`, not invented `score cp`. Do not fabricate `seldepth`, NPS, evaluation certainty or complete depths. Side-to-move polarity must be correct. A later evaluator/search failure invalidates prior provisional `info` as an action; diagnostics must be emitted, followed by engine process failure/termination rather than a fabricated successful `bestmove`.

**Draw extension exactly as approved:**

```text
info string chesslab decision claim_draw
bestmove e2e4
```

```text
info string chesslab decision claim_draw_with_intended_move g1f3
bestmove e2e4
```

Only the final, adjacent `info string chesslab decision` applies to the immediately following `bestmove` from this current search. The `bestmove` is the highest ranked **PLAY** at the last committed depth even when a claim was preferred; the claim remains authoritative for a trusted Chess Lab controller. M4/M5 rank every root candidate exactly, and the adapter may request an internal `multipv_count=256` to retain the best PLAY even when the configured displayed `MultiPV` is smaller. Verify this covers actual legal root candidates rather than assuming silently; external `info multipv` obeys requested output count. A selected claim with intended move *announces but does not play* that move. The fallback on cancellation before depth one is the canonical, explicitly unevaluated legal PLAY. A truly terminal root emits `bestmove 0000` with appropriate information, without inventing a draw claim. If no legal PLAY exists in a purported nonterminal state, treat it as an internal inconsistency, not a fabricated fallback. Invalid/failed search is a technical failure, not a valid chess decision.

**UCI extensions and trust.** Standard UCI engines may send arbitrary `info string`; the controller only interprets Chess Lab claim extensions for engine instances configured/trusted as our native executable and bound to its executable identity, not merely because a binary advertises `id name Chess Lab`. A provisional info string, multiple conflicting final claims, malformed intended moves, or a stale session are not accepted as authoritative. A non-Chess-Lab UCI engine's ordinary `bestmove` is interpreted solely as a proposed PLAY, never as an implied claim.

## 4. TypeScript controller, rules, authoritative history, and timing

**Local independent rules.** Pin an audited `chess.js` release under an explicit license; shield it behind the controller-owned `Rules` interface. Implement move legal validation and canonical FEN/UCI normalization without relying on engine subprocesses. The independent FIDE adjudicator owns checkmate/stalemate/dead-position handling; fivefold, 75-move automatic draws; threefold/50-move immediate and intended claims; exact claim-before-play semantics and precedence. Normalize en passant only if an en-passant *capture is legally possible*, considering king safety. Use occurrence signatures over placement, side, rights and legal EP; retain explicit complete/incomplete history. Partial record counts may prove a repetition threshold reached but cannot prove unseen earlier repetitions absent. Never call `chess.js.isGameOver()` as the sole outcome arbiter; separately verify dead-position/insufficient-material claims with agreed ChessCore fixtures. Always check mate/stalemate precedence before automatic 75-move draw where applicable.

**Authoritative game.** Immutable start FEN plus ordered *actually played* UCI moves and explicit history completeness are the replay source. Outcome/claim metadata are distinct records. The controller may maintain fast live board, repetition and clock projections but must periodically or at validation boundaries demonstrate they match replay. Only controller action commits a move or claim, and never from a provisional `info`. Tie to session id, game generation, expected root FEN/history and side-to-move. Before accepting any engine PLAY or claim, revalidate legality/outcome/time budget from authoritative rules. Invalid or stale output becomes protocol failure/ignored superseded result; do not apply its move. If user rank selection is supported, select only within exact completed ranking; never use provisional or bound-only scores.

**Clocks and deterministic events.** Untimed games and Fischer clocks only for M6. Use monotonic origin/deadlines; do not equate wall-clock `Date.now()` with elapsed playing time. A move timely *received* before expiry and later legally validated is charged through its captured monotonic receive instant; invalid messages do not retroactively stop the clock. On a valid completed PLAY, debit elapsed, grant configured increment then start opponent clock; accepted draw claims end game without increment and without playing announced move. A `stop` grace period never extends a game clock. Timeouts race using one explicit total order of captured timestamps/session events, with testable boundary cases. Analysis searches never mutate game state or consume player game clock unless explicitly operating in playing mode.

**Time-forfeit feasibility.** Introduce an adjudicator API representing `CAN_MATE`, `CANNOT_MATE`, `UNDETERMINED` for the non-flagging side, with explanations/test evidence. Sound impossible-case recognition may be conservative, never an over-broad `insufficientMaterial` shortcut. Constructive certified possibility witnesses or other documented sound proofs support `CAN_MATE`; mathematically proven impossible cases support `CANNOT_MATE`. If feasibility cannot be established for a position in M6's supported algorithm, mark `ADJUDICATION_REQUIRED`, pause interactive play, and stop/flag automated attempt as a separately reported unresolved adjudication—not as an arbitrary win/draw or clock extension. Do not silently replace strict FIDE with an approximate material table. The implementation checkpoint must state exactly which cases are provably covered and which remain unknown; add adversarial fixtures such as K+NN vs K, K+minor vs K, opposite minor pieces, self-blocking material, promotions, and rare cooperative mates.

## 5. Managed native UCI processes and session boundaries

**State machine:** STARTING -> UCI_HANDSHAKE -> READY -> SEARCHING -> STOPPING -> READY; FAILED/CLOSED are terminal for that process. One process has at most one outstanding `go`. A new `position`/`go` is forbidden while the previous `bestmove` is outstanding. After `stop`, wait for the old final `bestmove`, consume it as old even if superseded, then reconfigure/start new; if grace elapses, kill/replace the process instead of reassigning late output. A process replaced after error has a new generation. A search session ID lives in the controller and its result/progress objects, not on standard UCI wire. Session completion and cancellation are separate from whether its proposed move will be played.

**Protocol robustness:** Handle CRLF/line fragmentation, blank/unknown informational lines, concurrent stdout and stderr, bounded line/total buffered output, `uciok`/`readyok` deadlines, malformed or duplicate `bestmove`, premature exit, hanging `stop`, and an engine that prints the correct `id` but untrusted extensions. Validate announced UCI options and apply effective settings explicitly (including `ucinewgame`/`isready` ordering). Respect UCI `isready` while searching; do not treat arbitrary `readyok` as a search barrier. Spawn with validated executable and args, no shell evaluation and no arbitrary remote process control. Give each process explicit lifecycle/ownership; on failure, invalidate all pending sessions, release waits, dispose resources, and record diagnostics. No silent retry within an ongoing measured search.

**Failure policy:** Interactive game/analysis pauses with an error; automated match defaults to a labeled technical forfeit, or explicitly configured invalid-game disposition. Neither is a FIDE checkmate, clock timeout or draw. Capture process exit reason, protocol stage, command session, move number, timings and stderr excerpt within safe size limits. Separate match standings that include configured forfeits from chess-only W/D/L and paired statistics. If a failed process is restarted for a subsequent activity, hash/configure it anew and record distinct attempt provenance.

## 6. Reproducible headless experiments, durable records, API and CLI

**Experiment runner:** Reproducible paired games with the same opening/start FEN and swapped colors; deterministic schedule generated from an explicit recorded seed. Sequential execution for M6. Each scheduled game has immutable game id, pair id, color assignment and engine configuration hashes. Match uses independent state/history/clocks per game; no score comparison between unrelated evaluator scales. Provide fixed-position analysis/benchmark workflow with fixed-depth vs timed conditions identified separately. No new rating algorithm or inferential confidence estimate is required.

**Immutable manifests:** Record at minimum: schema version, creation time, manifest digest, experiment id, exact input engine executable path/hash and reported UCI identity/options/effective configuration, Chess Lab M2 artifact SHA/fingerprint/config when available, search depth/ordering/TT/certification/policy, clock and search allocation policies, openings and initial FENs, completeness metadata, random seed/schedule, platform/toolchain/Node/controller revisions, and expected result/forfeit policy. Record missing/unavailable fields *as unknown*, never invented. Option defaults must be captured as effective values, not assumed hidden third-party defaults. Engine identities may vary; avoid claiming bit-for-bit reproducibility for nondeterministic or timed runs.

**Filesystem schema:** A local experiment directory with immutable `manifest.json`, immutable `schedule.json`, durable per-attempt records (or recoverably appended `games.jsonl`), optional `games.pgn` and atomically rebuilt `summary.json`. Schema is versioned, validated and migration-aware. A finalized attempt includes unique attempt id, scheduled game id, start/current history, result disposition (chess/forfeit/invalid/unresolved), clocks/move log and diagnostics, effective config refs and measured stats. Claim events and technical events are represented outside the actual UCI move list/PGN moves. Serialize file writes atomically with proper flush/sync policy and detect torn tail writes; partial files are not counted as completed. No concurrent writers to the same experiment: lock and explicit stale-lock takeover after validation. Never rewrite finalized records or mutate manifest/schedule on resume. Completed games do not replay. Unfinished attempts remain as interrupted; explicit resume starts a new attempt from the originally scheduled start FEN, with new clock and engine processes. Attempt completion is idempotent under repeated resume/failure; a scheduled game contributes at most one authoritative terminal outcome. Export PGN with standards-compatible move/result tags while preserving Chess Lab-only metadata in associated JSON.

**Typed API and CLI:** Reusable `controller/` TypeScript module offers asynchronous engine lifecycle/search, game creation/play/claim, exact/provisional analysis subscriptions, timed play/stop, match run, manifest/status, resume and export. CLI is a thin adapter, not a second implementation. Provide at least `analyze`, `match`, `experiment status`, `experiment resume`, `experiment export` or equivalent discoverable commands and JSON config validation. Human stdout is concise; machine-readable structured output and deterministic nonzero errors are available. No HTTP/WebSocket API, browser UI, desktop server, accounts, external database or mobile transport for M6. Offline execution must work with pinned local dependencies after installation.

**Build/platform:** Preserve current native Debug/Release/Profile CMake/CTest and pinned Emscripten 4.0.10/SDK Node suites, including M5, unchanged in semantic coverage. Add a native-only UCI CMake target and Node/TypeScript lockfile/test/lint/typecheck commands. Wire Linux GitHub Actions to build and run controller integration against the native binary. Do not say Windows, macOS, real browsers or mobile work based solely on Linux native/Node CI. Pin dependency versions, document licenses and source-appropriate repo license terms. Report actual run environment, commands, CI links and failures, with `docs/m6-validation.md` and reproducible sample CLI configuration/transcripts. Stop if preexisting C++ ABI/rules must change; request review.

## 8. Non-goals, risks and handoff stop

- **No silent simplification** of strict FIDE draw claims, timeout checkmate-possibility, or engine error semantics. Fail closed/unresolved when proof unavailable; document accepted limitations and test them.
- **No uncalibrated cp** conversion from arbitrary White-positive M2 scores; mate distances and side-to-move signs are handled separately.
- **No UCI session IDs on the standard wire.** Serialize processes and await barriers; extension trust is explicit and independent of `id` spoofing.
- **No M7/M8 work**: GUI/React/HTTP/WebSocket/Capacitor/WASM Worker, pondering, book, selective search/quiescence/Decision 24 research, parallel/distributed matches, broad rated-tournament rules and Elo/uncertainty research are deferred.
- Key risks for Codex design checkpoint: (i) proving time-forfeit feasibility without heuristic overclaiming, (ii) exactly-once UCI session finalization under races, (iii) final draw extension + best PLAY fallback without fake cp or partial depths, (iv) durable append/crash recovery and idempotent pairing outcomes, (v) safe evaluator/TT ownership through native command-thread/worker transitions.

**Implementation gate:** Both this spec and `docs/codex-kickoff-m6.md` must be approved and merged into `main`. Codex implements on a separate `m6/headless-controller` branch, opens one implementation PR with actual tests/evidence, and **stops without merging**. An M6 feature omission must be stated explicitly; do not declare acceptance solely from compilation, mocked tests or unobserved CI.
