# M7.3 — Prepared Search Nodes and Draw-Claim Metadata

**Status:** Approved architecture; draft implementation in PR #19, under correctness and performance review.  
**Baseline:** `chess-engine-lab`, merged M7.2 PR #18, main revision `17edf1e438370d8fc1dc17db66982b3fd0d5cf85`.  
**Evidence:** The supplied *Initial-position search performance after M7.2* investigation and its Release, diagnostic-counter, and sampling CSVs.  
**Intended repository path:** `docs/m7.3-search-node-design.md`.

## 1. Objective and measured motivation

Provide each search-node encounter with one prepared, position-specific legal-move list and shared rule metadata. Compute optional draw eligibility once, store it as node/move metadata, and consume it throughout terminal handling, TT access, leaf evaluation, and alpha-beta traversal. Avoid regenerating legal moves through `status()`, `encode_move()`, `make_move()`, or repetition/en-passant normalization on the trusted internal search path.

At initial-position depth six with TT off, the provided Release investigation records **17,862.088 ms**, **381,938 visited nodes**, **328,475 evaluations**, **9,440,437 prospective claim child probes**, and **88,751,792 complete legal-move generations**. Of those generations, **58,903,019** are attributed to raw-EP normalization and **75,912,579** to `require_legal()` invoked from `encode_move()`. The 9.44 million prospective claim probes found **zero** eligible intended claims in that workload. Sampling attributes about **84.68%** inclusive samples to `Traversal::claim`; inclusive percentages overlap and are not additive. Cold/warm numeric TT at depth six took about 22.7 seconds, versus 17.9 seconds with TT off, under the measured 8 MiB request. These are baseline observations, not speedup forecasts.

### Explicitly in scope

- Search-internal prepared-node representation, ownership, lifetime and propagation.
- Reuse of one legal list for terminal detection, canonical encoding, PV/TT ordering, intended draw claims, and traversal.
- Exact repetition signature built from the prepared board snapshot and legal-move list, including legal-EP availability.
- One-time node-level and per-move optional claim metadata, using sound inexpensive negative filters and exact checks for exceptional candidates.
- Trusted-search-path move encoding/application without repeated full-list validation, while retaining public input-validation behavior.
- Identical externally observable search decisions, scores, PVs, terminal handling and provenance.

### Out of scope

No change to the material evaluator, evaluator ABI, chess rules, quiescence/selective search, engine strength heuristics, time controls, threading, TT proof requirements, TT replacement strategy, or UCI/controller draw-claim policy. Optimizations must be separately benchmarked and correctness-tested. This design does **not** treat a draw claim as an ordinary move with an altered score.

## 2. Normative principles

1. **One legal list per encounter.** A prepared search-node encounter creates one complete set of legal moves for its current, immutable-at-preparation board state. Every search-internal consumer uses that set. Order can change; membership and associated metadata cannot.
2. **EP is an ordinary member of the legal set.** Legal en-passant captures appear among generated moves and carry normal move identity/metadata. Raw EP is retained in the position/evaluator snapshot; the normalized *repetition* EP field is present iff the prepared list contains a legal EP capture. No subsequent EP-specific legal-list generation occurs.
3. **Compute and retain draw eligibility.** Immediate claim availability belongs to the node. Intended-move eligibility belongs to the corresponding `LegalMoveInfo`. Each flag is a verified assertion, not an estimate. Search never repeats eligibility checks after preparation.
4. **Claims are distinct actions.** `claim_draw` and `claim_draw_with_intended_move` are alternatives to `play`, each with score zero and existing canonical decision precedence. An intended move announced with a claim is *not actually played* by that action. A PLAY action still evaluates normally even if that move could have supported a claim.
5. **Do not eagerly materialize children.** In the common case, node preparation determines that intended claims are impossible without making *any* prospective move or generating child legal lists. Only history-qualified exceptional candidates require exact child inspection. If exact inspection produces a prepared child, its ownership is retained for subsequent traversal where feasible.
6. **Preserve contracts.** Automatic-terminal precedence, history correctness, invalid-input protections, cancellation/error restoration, exact PV/tie-breaking, TT context certification and M7.2 root policy remain unchanged.

## 3. Proposed internal data model (illustrative C++20)

Types and names below are an internal design; they are not a request to modify the stable M2 evaluator ABI or publish additional C++ APIs.

```cpp
struct MoveFacts {
    bool pawn_move = false;
    bool capture = false;            // Includes en passant
    bool legal_en_passant = false;   // Established by legal generator
    bool resets_halfmove = false;   // pawn_move || capture
};

struct ClaimFlags {
    bool threefold = false;
    bool fifty_move = false;
    bool any() const noexcept { return threefold || fifty_move; }
};

struct LegalMoveInfo {
    std::unique_ptr<Move> move;       // Opaque adapter move, from THIS position
    std::string uci;                 // Encoded once, canonical and unique
    MoveFacts facts;
    ClaimFlags intended_claim;      // Fully resolved before search consumes it
    // Rare-case optional cached prepared child: owned, scoped, or materialized
    // through a safe continuation handle; never a stale pointer after undo.
};

struct PreparedNode {
    // Board/position lifetime is owned by traversal, not copied blindly.
    // All move objects are valid for the position generation that prepared them.
    ChessEvalPosition eval_state;    // If validated once, reuse this conversion
    RepetitionSignature signature;   // normalized using THIS node's legal moves
    std::vector<LegalMoveInfo> legal; // One generated list, canonical at creation
    bool in_check = false;           // Needed only when legal is empty
    bool known_dead = false;         // Preserves existing dead-position policy
    bool claim_now_threefold = false;
    bool claim_now_fifty_move = false;
    bool automatic_fivefold = false;
    bool automatic_seventy_five_move = false;
};
```

Represent actual cached child state separately from `LegalMoveInfo` if needed to avoid copying move-only objects or invalidating position provenance on undo. A `PreparedChild` should either (a) own its exact `Position` plus already-generated legal list, and be traversed directly, or (b) hold enough certified, generation-independent data to reconstruct without another full legal-list generation. Do **not** cache opaque position-bound move objects across make/undo unless the adapter establishes their validity. The implementation should choose and test one ownership model before performance changes are merged.

A `HistoryCounts` index must track exact `RepetitionSignature` occurrence counts for the active actual search path, independent of whether a TT is attached. The current history vector remains available for provenance and exact verification. Push/pop must be exception-safe and restore both representations. Count maps may be reused by the TT session; do not require TT enablement merely for efficient threefold candidate detection.

## 4. Node preparation and traversal sequence

### 4.1 Initialization and root handling

1. Validate options, evaluator identity/usable state and root/history consistency in the existing contractual order. Root-history signature comparison should reuse a prepared root signature instead of invoking a second EP-normalizing legal generation. Public `GameHistory::matches_root` remains valid for outside callers.
2. Create a prepared root with a single legal-move generation; preserve its canonical move ordering and reuse it for terminal/fallback detection and iterative depths. A new iteration may reorder its own view without mutating canonical identity.
3. Initialize the exact history occurrence index from supplied `GameHistory`, respecting complete/incomplete provenance.
4. Preserve M7.2 `MultiPV=1 && single_pv_play_only=true`: actual root PLAY-only, *no optional root claim selection*, and no TT root probe/store. Legacy root and MultiPV paths continue to support claim alternatives.

### 4.2 Prepare a new node encounter

**A. Generate and annotate legal moves once.** Get one set from `core.legal_moves(position)`, produce UCI strings without regenerating legal moves, attach move facts, check canonical uniqueness and preserve stable move identities. The production adapter may expose an internal trusted-certificate fast path; the public `ChessCore::encode_move` and `make_move` must still reject invalid/foreign/stale input as before.

**B. Build snapshot and repetition identity.** Reuse one board snapshot/conversion. Build `RepetitionSignature` from pieces/side/castling; its normalized `legal_ep` is the raw EP square only if a legal EP capture appears in the prepared list. Do **not** mistake raw EP in FEN/evaluator state for legal EP in repetition identity.

**C. Classify mandatory terminal results in existing precedence.** If legal list empty, use `in_check` to distinguish mate from stalemate. Otherwise apply existing `known_dead_position`, fivefold repetition and 150-halfmove automatic draw checks. Preserve mate/stalemate precedence over automatic-draw checks. If terminal, do not perform optional-claim processing or evaluator calls.

**D. Produce claim metadata exactly once.** If this is a claim-aware node, determine immediate claims and annotate intended claims according to §5 below. If it is the M7.2 PLAY-only root, do not spend time annotating optional root claims. Store separate claim action candidates; never alter normal PLAY scores.

**E. TT access and search.** Reorder the *same* annotated legal list using previous-PV/TT hints; preserve original canonical ordering for deterministic decision-tie rules. Probe TT only after required terminal/claim obligations, retaining exact context verification. At depth zero, consult applicable TT or evaluate directly. At positive depth, use alpha-beta traversal and possible exact-PV re-search. On return, store eligible TT result with the original window and same proof semantics.

**F. Restore state.** Any child exploration restores the complete board, history vector, occurrence map, TT session tail, PV path and legal-list ownership on success, cancellation or failure. Do not let preparation/cached child state leak across mutated positions.

### 4.3 Child-entry invariant

The parent's selected legal `Move` was generated from the parent state. On entering a child, create exactly one child prepared list and use it both to establish the child's repetition signature/history and to process the child's terminal/claim/search logic. The current M7.2 implementation calls `repetition_signature` within `Traversal::child()` before recursive `node()`; this ownership/sequence must be refactored. Search result counters should continue to count **visited recursive nodes**, not unsearched prospective claim inspections.

## 4.4. Illustrative control flow

This pseudocode states the intended ownership boundaries; it is **not** drop-in C++ or a change to the public interface:

```cpp
// The caller owns the current Position and active exact history.
Line visit(Position& position, PreparedNode&& ready, int depth,
           Bounds bounds, RootPolicy root_policy) {
    count_visited_node();
    if (auto terminal = classify_terminal(ready, history_counts))
        return finish_and_maybe_store(*terminal);

    if (root_policy != RootPolicy::play_only)
        resolve_optional_claim_metadata_once(ready, history_counts);

    auto best = claim_action_alternative(ready, root_policy); // score zero
    order_existing_moves(ready.legal, previous_pv, tt_move_hint);
    if (auto certified = probe_tt_after_required_rule_checks(ready, bounds))
        if (certified->can_answer_this_request)
            return finish_and_maybe_store(*certified);

    if (depth == 0)
        return finish_and_maybe_store(
            better_of(best, evaluate_existing_snapshot(ready.eval_state)));

    for (LegalMoveInfo& m : ready.legal) {
        // No revalidation/full legal generation for an already trusted move.
        // If a rare claim check prepared this child, safely adopt that state.
        ChildVisit child = enter_child_once(position, m);
        Line answer = visit(child.position, std::move(child.ready),
                            depth - 1, narrowed(bounds), RootPolicy::normal);
        restore_exact_parent(child);
        update_best_pv_and_bounds(best, answer, m.uci);
        if (bounds.closed()) break;
    }
    return finish_and_maybe_store(best);
}
```

The implementation must also preserve M7.2's exact-PV re-search and canonical tie refinement, which are intentionally abbreviated above. `prepare` and `enter_child_once` must not silently create a second legal list for the same child encounter.

## 5. Precise draw-claim rules

### 5.1 Node-level immediate claims

After mandatory-terminal classification:

```cpp
node.claim_now_threefold   = history_counts[node.signature] >= 3;
node.claim_now_fifty_move = node.eval_state.halfmove_clock >= 100;
```

Either flag makes `ChessDecision{DecisionKind::claim_draw, ...}` available, with score 0. If immediate claim is available, existing M7.2 `claim()` semantics do **not** search for intended-move claims at that node; maintain the same canonical precedence.

### 5.2 Per-move intended fifty-move claim

Only when **no immediate claim** is available, for each legal move `m`:

```cpp
m.intended_claim.fifty_move =
    node.eval_state.halfmove_clock >= 99 &&
    !m.facts.resets_halfmove;
```

For ordinary valid positions without immediate claims the threshold effectively is 99; use the predicate appropriate to clock-boundary tests and the existing terminal precedence. No hypothetical move, child snapshot or legal-move generation is needed. Pawn moves, including promotions and en passant, reset the clock; all captures reset it. **Do not use `m.isCapture` alone** to classify pawn moves.

### 5.3 Per-move intended threefold claim

For a legal move `m`, the proposed child position permits an intended threefold claim iff:

```text
history_counts[exact_repetition_signature(result_of(m))] >= 2
```

The current position is already in `history_counts` once; an intended claim announces the move but does not execute it as the chosen action. Repetition identity includes pieces, side, castling rights and **legal** EP availability, not raw EP or halfmove/fullmove clocks.

**Sound negative filter (common case).** If no exact signature in the active history has an occurrence count of two or more, set `m.intended_claim.threefold=false` for **every** move, without applying any hypothetical move. This filter is necessary-condition logic, not a heuristic.

**Exceptional case.** When repeated targets exist, test only potential matches. First match inexpensive derived characteristics (at minimum child side to move; optionally cheaply predicted piece placement and castling rights). Rejecting a potential match must be provably sound. For remaining candidates:

1. Derive/apply the selected *already legal* move using an internal trusted method, not a repeated legal-list validation.
2. Obtain the exact child repetition identity, including legal EP normalization. If child legal moves are required to establish EP, prepare them **once** and retain the prepared child for actual later traversal where possible. Do not invoke `ordered_moves()` a second time as an EP-specific subroutine.
3. Look up this exact child signature in history counts; set threefold flag iff previous count is at least 2.
4. Undo/restore any transient state, without modifying the actual search-path history or persistent TT push/pop as part of claim eligibility checking.
5. Retain any result needed to prevent duplicate child preparation if that move is subsequently traversed. Do not retain stale position-bound move certificates.

An implementation can choose a more efficient exact child-key derivation, but must prove equivalence with the existing legal-EP signature before eliminating child-list construction. The specification does **not** mandate eagerly generating every child's legal list.

### 5.4 Claim selection and evaluation

- If at least one immediate claim exists, produce the existing `claim_draw` alternative (score 0).
- Otherwise, select the canonically first legal move with either intended flag as the existing `claim_draw_with_intended_move` alternative (score 0). Retain the current tie ordering of decision kinds and move strings; PV end and intended move fields must match M7.2.
- Search normal PLAY moves independently. They may have a negative or positive score regardless of whether they support a claim. The maximizing/minimizing player chooses between ordinary PLAY and separate claim alternatives; maintain existing alpha-beta boundary semantics.
- Do not treat a claimed draw as an automatic terminal simply because a move metadata flag is true. Fivefold/75-move automatic rules remain separate.

### 5.5. Worked examples

- **Typical opening node, halfmove clock 0, no repeated historical target:** generate the current legal list once; mark all intended threefold and fifty-move flags false; perform *zero* speculative child move applications for claim checking. Search still explores child moves normally at positive depth.
- **Clock 99, quiet legal move:** attach `fifty_move=true` to that move directly from the move facts. A pawn move or capture has `fifty_move=false`; no child position is needed to decide either flag.
- **Current position already threefold:** store an immediate `claim_draw` candidate and skip intended-claim checks; still search ordinary PLAY moves when the node is nonterminal.
- **History contains a repeated target:** examine only legal moves that may reach it. Verify the child signature exactly, including whether *that child* has a legal EP capture; retain any prepared child needed for subsequent search without violating position ownership.

## 6. Trusted move handling and adapter boundary

The existing native `Core::encode_move()` and `Core::make_move()` each call `require_legal()`, which regenerates the complete legal list. Replace **redundant internal verification** for a generated, position-matched move with an adapter-private certificate or equivalent trusted operation. A certificate must bind move identity to its originating position generation; it becomes invalid after board mutation, undo/reset/clone as applicable. For untrusted/foreign/stale externally supplied moves, fall back to full validation or preserve existing rejection behavior.

Do not assume that a move accepted for a parent is automatically legal for a sibling or identical-looking later position. `make_move` still performs state transitions, metadata checks and throws on overflow; `undo_move` retains its existing identity/LIFO/single-use guarantees. Keep opaque third-party `chess::Board` and `chess::Move` types behind the `ChessCore` abstraction. If internal helpers are added, either support non-native test adapters or supply a contract-preserving generic fallback. Avoid changing the public evaluator ABI or inadvertently changing public exception/error ordering.

## 7. Repetition, en passant and history invariants

1. A node's legal EP capture(s), if any, are in the same generated legal list. Pinned/illegal EP candidates do not appear; a raw EP target with no legal EP capture normalizes to `nullopt` in the repetition signature.
2. Raw EP, halfmove and fullmove counters continue to be retained exactly in evaluator-visible snapshots and TT state. They are not folded into repetition equality. Castling rights and side to move **are** included in repetition equality.
3. History counts include the current node occurrence **before** checking immediate claims; for an intended-move claim the unplayed resulting position is compared against counts **without** adding its hypothetical occurrence.
4. The exact history vector, counts index and TT session tail remain synchronized through all actual traversed child transitions, exact-PV re-searches and cancellation/error paths. Cheap read-only lookahead for a claim must not modify them.
5. An automatic terminal result is determined before optional claim alternatives. Maintain the M7.2 actual-root policy and distinguish score bounds from publishable exact PVs.
6. A prepared list must never be reused after the board position/generation has changed, unless separately owned as a matching immutable prepared child. Canonical order and stable move metadata travel together through move ordering.
7. Do not assume a repeated-position hash alone proves identity; equality uses exact `RepetitionSignature`. Preserve TT's deeper evaluator, history and bound proof requirements unchanged.

## 8. Instrumentation and acceptance criteria

Implement low-overhead aggregate counters **only in diagnostic builds**, not canonical Release benchmarks:

- prepared nodes and full legal-generation calls, attributed to root, node, and rare claim-child preparation;
- trusted fast-path vs fallback move-encode/apply validations;
- nodes with immediate claims, nodes rejected by no-repeated-target filter, intended-claim candidates inspected, confirmed threefold/50-move intended claims;
- child-list reuse counts, raw-EP positions and legal-EP normalization results;
- search nodes, evaluator calls, alpha-beta cutoffs, TT probe/store/hit/verification and history push/pop counts;
- Release elapsed time, CPU time, exact decision/score/PV checksum for each completed iteration.

**Correctness gate:** Preserve exact decision, score, intended move, PV and PV end at every completed depth, for fixed-depth and iterative paths, TT off/hint-only/cold/warm numeric, both root policies, both colors and multiple FEN/history fixtures. Preserve terminal, history, evaluator failure, cancellation, timeout-owner, and progress-commit contracts. No stochastic or weakened repetition/TT proof is accepted.

**Performance gate:** Measure native Release with the same initial FEN/material evaluator and workload as the attached investigation: depths 4/5/6, single-PV PLAY-only root, alpha-beta/previous-PV ordering on, TT off/cold/warm separately, serial runs, identical warmup/reporting rules, and no diagnostic timers in timed binaries. Compare to initial-position baseline **99.330 / 1,580.016 / 17,862.088 ms** for TT-off depths 4/5/6. Report median of three, nodes, true legal-generation calls, prospective-probe calls and checksums. No speedup threshold is asserted in advance; require a material measured improvement to justify merge.

**Required regression families:**

- M1 legality, castling, promotion, EP (legal, impossible and pinned), make/undo/perft, foreign/stale/invalid moves and counters.
- M3 history, immediate and intended threefold/50-move claims, mate/stalemate/dead/fivefold/75-move precedence, incomplete history and canonical intended-move selection.
- M4 iterative/depth-commit, previous-PV ordering, MultiPV, cancellation, exceptions and root fallback.
- M5 TT hint/numeric, collisions and exact history verification, policy/fingerprint/context mismatches, PV re-searches, pool capacity, mid-verification cancellation and exclusive ownership.
- M7.2 single-PV root no-claim/TT separation and legacy root; equal-score/canonical ties, all-depth exact-result checksums.
- Explicit clocks 98/99/100/149/150; pawn/capture/quiet move; both colors; history counts 1/2/3/4/5; raw EP vs legal EP; position replay and restored state.

## 9. Incremental implementation and review gates

**Step 0 — Golden baseline.** Freeze existing test hashes, timings and diagnostic counts; add fixtures for the new node/claim-metadata invariants. No production logic change.

**Step 1 — Prepared legal list and terminal reuse.** Introduce a prepared-node helper and consume one generated list for `status` equivalence and canonical ordering. Introduce a trusted adapter-private move provenance path, with tests proving public validation remains intact. Benchmark independently.

**Step 2 — Prepared repetition identity.** Derive normalized legal EP from the prepared list rather than `ordered_moves()` in search-internal repetition generation. Change child-entry ordering so a child is prepared once before its identity is appended. Preserve public `repetition_signature()` as a contract-preserving wrapper/fallback. Benchmark and verify complete/incomplete histories.

**Step 3 — Draw metadata.** Add `ClaimFlags`, cheap fifty-move derivation and indexed repeated-target negative filter; compute verified threefold flags for candidates and retain rare prepared-child state safely. Replace `Traversal::claim()`'s hypothetical all-move loop with consumption of flags. Benchmark TT off and numeric TT separately.

**Step 4 — Consolidate and review.** Reuse snapshots/ABI conversions when safe, verify TT bookkeeping is no longer performed for mere prospective claim inspection, and run all search suites and serial clean Release benchmarks. Decide separately whether additional TT redesign or selective search work is warranted.

Each step must preserve exact outcomes and be reviewable independently. If a step fails a correctness or throughput gate, revise or revert it before proceeding. Do not bundle speculative algorithmic changes with the architectural refactor.

## 10. Implementation questions to resolve before code changes

1. **Prepared-child lifetime:** Choose a concrete ownership strategy ensuring rare claim candidates are not redundantly prepared when actually traversed and that no opaque move survives a mismatched position generation. Model clone/make/undo costs before committing to a strategy.
2. **Adapter trust certificate:** Decide whether to extend a private native `Mv` with origin identity/generation and a validated-legal bit, or introduce a separate search-only capability. Document the generic fallback for test adapters and externally provided legal moves.
3. **Root validation:** Refactor only the internal root validation path to reuse the prepared signature while preserving public `GameHistory::matches_root` and error behavior.
4. **History target filtering:** Start with the provably safe `any count >= 2` check. Add derived child-key filtering only with explicit proofs and edge-case tests; never reject a genuine potential match from a hash collision or raw-EP mismatch.
5. **Statistics:** Keep `visited_nodes` semantics unchanged. Report separately any speculative exact child preparations and cached child reuses.

**Design approval is separate from implementation approval.** This document is intended for agreement on data ownership, preparation order and invariants before production code is edited.
