# Reversible iterative-search ordering

M7.6 integrates the reviewed B2 compact best-only ordering as the **default**.
The full categorical P1 implementation is retained in the repository. One CMake
cache setting selects the representation; there is one shared search traversal:

| `CHESS_LAB_ORDERING_POLICY` | Behavior |
| --- | --- |
| `B2` (default) | One preferred move per retained parent, compact path links |
| `P1` | Full categorical sibling preferences |
| `NONE` | Original G1b previous-PV/TT ordering, no persistent tree |

All entry points linking `chess_search`, including native UCI and WASM, use the
selected policy. Controller and GUI use the policy of the native executable they
launch; rebuild/re-register that executable if its path changes. Fixed-depth
non-iterative search has no previous-iteration tree. No public search interface,
evaluator ABI, UCI option, controller protocol or persistence format changes.

## Select, verify and switch back

Run from an x64 MSVC developer shell on Windows or a C++20/Ninja Linux shell:

```sh
cmake --preset native-release -DCHESS_LAB_ORDERING_POLICY=P1
cmake --build --preset native-release
ctest --preset native-release
```

Switch back with exactly the same commands, changing only `P1` to `B2`.
`NONE` selects G1b ordering. An existing CMake cache retains its selection;
omitting the flag does not reset an existing P1 cache. Fresh builds default B2.
No code edits, patch reconstruction or historical artifacts are needed.

Configure prints `CELab ordering policy: ...`; `build/native-release/ordering-policy.txt`
and `CMakeCache.txt` record the selection. Run
`build/native-release/m76_policy_smoke` (`.exe` on Windows) for the compiled-policy
diagnostic and normal public-entry-point checks. This diagnostic is compiled
with the same exported target definition as the library, not a runtime selector.

Use `native-debug` or `native-profile` in the same three commands for other native
configurations. For pinned Emscripten 4.0.10, activate the SDK described in
[local-ci.md](local-ci.md), then:

```sh
cmake --preset wasm-debug -DCHESS_LAB_ORDERING_POLICY=P1
cmake --build --preset wasm-debug
ctest --preset wasm-debug
```

WASM active policies enable memory growth for bounded retention allocation.
SDK Node 22.16.0 remains separate from application Node 24. Neither policy needs
threads or native plugins in WASM. This is Node/WASM correctness coverage, not
browser integration validation.

## Semantics and memory

Each iterative invocation owns a fresh tree, retaining plies 0–3 between completed
depths. Only completed iterations commit retained preferences. Existing canonical
ties, exact PV refinement, previous-PV/TT precedence, claims, cancellation and
rollback are preserved. No recency, cost-aware or new ordering heuristic is added.
Policy selection is compile-time: no virtual dispatch or runtime policy switch.
B2 never instantiates the P1 arena. Internal scoped controls remain test seams;
normal search activation does not depend on them.

Both active policies have the validated 128 MiB ceiling, including their existing
accounting/fallback behavior. P1 reserves approximately that amount per concurrent
invocation. B2 allocates on demand (maximum observed reserved 3.28 MiB and peak
accounted 4.66 MiB in the adoption corpus); its general ceiling is still 128 MiB.
Those observed values are not universal maxima. Resident process memory differs
from reserved/live payload. NONE makes no persistent-retention allocation.
Budget exhaustion retains each frozen policy's safe fallback; comparison
fixtures require zero fallbacks. Do not lower capacity and claim equivalent
retention coverage.

## Maintained verification and provenance

`m76_ordering` preserves the original adversarial/synthetic/native policy tests.
`m76_policy_smoke` exercises normal API activation, exact public/MultiPV output,
work parity against explicit selected configuration, restoration and allocation.
`m76_policy_build` builds B2, P1 and NONE in isolated child build directories and
runs their smoke tests plus the B2/P1 correctness suites. It runs in normal native
and WASM CTest; child builds disable only recursive matrix registration. Local
CI requires the smoke/build tests in its inventory. Existing assertions and
timeouts are unchanged; new tests have their own 300-second limits.

frozen adoption references, based on G1b
